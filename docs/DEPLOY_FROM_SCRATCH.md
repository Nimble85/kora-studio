# Розгортання KORA Studio з нуля

Ця інструкція описує нову інсталяцію застосунку та **порожній** проєкт Supabase. Для оновлення бази з даними використовуйте [інструкцію міграції](SUPABASE_MIGRATION.md): не запускайте початковий seed повторно в робочій базі. Код, база даних і конфігурація хостингу розгортаються окремо.

## 1. Підготуйте код і середовище

1. Клонуйте репозиторій `https://github.com/Nimble85/kora-studio.git` та перейдіть у його каталог.
2. Встановіть сумісну з Next.js 16 версію Node.js і перевірте її командою `node --version`. Використовуйте `package-lock.json` як джерело версій пакетів:

   ```bash
   npm ci
   npm run lint
   node node_modules/next/dist/bin/next build
   ```

3. Зафіксуйте commit SHA, який плануєте розгорнути (`git rev-parse HEAD`). На хостингу розгортайте цей самий коміт. Попередження lint перегляньте; помилки lint або build зупиняють випуск.

Не додавайте `.env.local`, SQL-паролі чи дані клієнтів у Git і логи. Файл `package-lock.json` змінюйте лише під час свідомого оновлення залежностей.

## 2. Створіть порожню базу Supabase

1. Створіть окремий проєкт Supabase. Збережіть його Project URL та **anon/publishable** ключ у налаштуваннях проєкту; не використовуйте service role key у `NEXT_PUBLIC_*`.
2. У SQL Editor **цього проєкту** виконайте весь [`supabase/schema.sql`](../supabase/schema.sql) **один раз**. Він створює таблиці, включно з чотирма полями МК у `sales`, і додає 20 нових позицій каталогу. У ньому є `CREATE POLICY`, тому повторний запуск цілого файлу може завершитися помилкою на вже створених політиках.
3. Після успішного створення схеми виконайте весь [`supabase/seed-products.sql`](../supabase/seed-products.sql) **один раз**. Він додає початкові 40 продуктів, 19 матеріалів і безпечно пропускає 20 позицій, які вже створив `schema.sql`. Seed не створює продажів чи витрат.
4. Перевірте саме цю базу:

   ```sql
   SELECT count(*) AS products FROM public.products; -- 60 у новій базі
   SELECT count(*) AS materials FROM public.materials; -- 19 у новій базі
   SELECT count(*) AS sales FROM public.sales;       -- 0 у новій базі

   SELECT column_name
   FROM information_schema.columns
   WHERE table_schema = 'public' AND table_name = 'sales'
     AND column_name IN ('workshop_at', 'deposit', 'candle_choices', 'instagram_url')
   ORDER BY column_name; -- 4 рядки
   ```

Не використовуйте кількість 60 як критерій для наявної бази: власник може додати, видалити або архівувати товари. Для неї перевіряйте ID міграції за [інструкцією](SUPABASE_MIGRATION.md).

## 3. Налаштуйте застосунок

У локальному середовищі створіть `.env.local` за зразком `.env.example`; на хостингу внесіть ті самі змінні в налаштування середовища:

```text
NEXT_PUBLIC_SUPABASE_URL=<Project URL саме цієї бази>
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon/publishable key цього проєкту>
```

Значення `NEXT_PUBLIC_*` потрапляють до браузера. Після зміни змінних **перезберіть і повторно розгорніть** застосунок. Якщо їх немає, застосунок працює в локальному режимі: записи живуть у `localStorage` одного браузера й не синхронізуються з Supabase. Переконайтеся, що в інтерфейсі показано «Синхронізація з Supabase», коли очікується віддалене зберігання.

Поточний екран входу є клієнтською перевіркою, а політики Supabase у схемі дозволяють операції без прив'язки до конкретного користувача. Це придатне лише для обмеженого пілота. **Перед публічним або багатокористувацьким запуском** потрібні серверна автентифікація, політики RLS для користувачів та резервне копіювання. Паролі й доступ до Supabase не налаштовуйте через публічні змінні середовища.

## 4. Запустіть або розгорніть

- Для локальної перевірки: `npm run dev` і відкрийте `http://localhost:3000`.
- Для самостійного Node-хостингу: після `npm ci` і успішного build запустіть `npm run start`; налаштуйте HTTPS і доступ до сервера відповідно до свого хостингу.
- На керованому хостингу імпортуйте репозиторій як Next.js-проєкт, внесіть змінні з розділу 3, запустіть build та перевірте, який commit SHA розгорнуто. Назва й команди конкретного провайдера можуть відрізнятися.

Git push або деплой **не запускає SQL**. Для наявного проєкту Supabase перед новим кодом виконайте [`supabase/migrations/20260921_workshops.sql`](../supabase/migrations/20260921_workshops.sql), зробіть резервну копію та перевірте результат за [інструкцією міграції](SUPABASE_MIGRATION.md). Окремий SQL лише для чотирьох полів усуває `42703`, але залишає старий каталог із 40 позицій.

## 5. Перевірте після запуску

1. Відкрийте застосунок на телефоні й комп'ютері. П'ять нижніх вкладок мають залишатися в одному рядку, а плаваючий плюсик — не перекривати навігацію.
2. У «Ще → Каталог» перевірте звичайний кокос і категорію МК. У новій базі має бути 60 продуктів. Плюсик пропонує чотири дії; МК обирається через **Продаж → вибір продукту → Майстер-класи**.
3. Створіть тестовий продаж МК із датою, двома видами свічок і частковою передплатою. Перевірте червоний залишок, календар та редагування. Оновіть сторінку й переконайтеся, що запис зберігся; після перевірки видаліть лише власний тестовий запис.
4. Перевірте закупку, залишки складу та фінансові показники. Пройдіть повний [`RELEASE_CHECKLIST.md`](RELEASE_CHECKLIST.md).

Якщо завантаження показує `42703: sales.workshop_at`, перевірте SQL і Project URL тієї бази, яку читає деплой. Якщо видно 40 товарів, перевірте вставку 20 позицій міграції. Якщо на екрані «лише цей пристрій», перевірте змінні середовища й повторний build.

## Відновлення

При невдалому випуску зупиніть запис нових даних, збережіть поточний стан і поверніть **попередній коміт застосунку** на хостингу. Адитивні поля та seed не потребують видалення для відкату коду. Не запускайте `DROP TABLE` і не відновлюйте стару копію бази поверх нових продажів без окремого плану збереження записів. Виправте причину на тестовому середовищі й повторіть перевірки перед новим деплоєм.
