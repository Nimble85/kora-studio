# Нотатки для наступних ітерацій

Це робочий список для наступного агента. Починайте із [`AGENTS.md`](../AGENTS.md), [`DATA_MODEL.md`](DATA_MODEL.md) та [`DEPLOY_FROM_SCRATCH.md`](DEPLOY_FROM_SCRATCH.md). Перед редагуванням перевіряйте `git status --short`; у робочому дереві можуть бути чужі незакомічені зміни. Не припускайте, що SQL-міграція виконалася разом із деплоєм коду.

## Найближчий пріоритет: надійний випуск

1. **Доказ стану схеми.** Додати керований журнал версій міграцій та preflight-перевірку необхідних таблиць і полів до завантаження всього екрана. Якщо бракує `sales.workshop_at`, показувати конкретну інструкцію для правильного Supabase-проєкту. Не підставляти демо-дані замість робочих записів. Приймання: стара схема дає зрозумілу помилку, повна схема завантажує дані, застосування міграції не створює дублікатів.
2. **Початкове наповнення.** Розділити `schema.sql` (структура) та seed (початковий каталог) без повторної вставки позицій 41–60. Зробити seed повторюваним без перезапису цін, змінених власником, і документувати відхилення від базових 60 продуктів. Приймання: новий проєкт і повторний запуск seed дають однакові 60 продуктів та 19 матеріалів без продажів.
3. **Доступ до даних.** Поточний логін перевіряється в браузері, а SQL-політики `using (true)` відкривають доступ через публічний ключ. Перш ніж відкривати систему іншим користувачам, запровадити реальну автентифікацію, прив'язку рядків до власника й RLS; перевірити відмову доступу для іншого користувача. Не вважати теперішній екран входу захистом Supabase.
4. **Резервні копії.** Описати й перевірити відновлення бази та експорт локальних записів. До змін схеми створювати контрольну копію; не скидати таблиці чи локальне сховище для виправлення міграції.

## Наступна продуктова ітерація

- **МК і платежі.** Зараз `sale.amount` — повна ціна, `deposit` — передплата, а залишок обчислюється як різниця; наступні платежі не мають власних записів. Узгодити, чи виручка має означати суму договору або фактично отримані кошти, перш ніж змінювати фінансові формули. Для часткових і повторних оплат потрібні події платежів та міграція старих продажів. Перевірити повну/часткову оплату, редагування та звіт за різні дати.
- **Події календаря.** Наразі кожна подія походить від продажу і групується за датою та збереженою назвою товару. Продажі однакового типу після перейменування можуть розійтися по різних групах; подію без продажу створити не можна. Наступний крок — окрема сутність МК/сеансу з учасниками, місткістю й посиланням із продажу. Міграція повинна зберігати всі старі бронювання.
- **Форма продажу.** Чотири дії плюсика залишаються за вимогою власника. Додати помітний вхід до МК у межах продажу, якщо користувачам важко знайти категорію. Для МК приховати підпис «Обсяг воску ще не задано» у каталозі. Помилки валідації показувати поряд із відповідними полями, а не лише загальним банером.
- **Нагадування й дати.** Значення `today` обчислюється під час завантаження модуля. Перевірити роботу відкритої вкладки після опівночі за Києвом, зміну місяця й часові пояси. Нагадування зараз існує лише всередині застосунку, за 0–3 дні до дати; не називати його push-сповіщенням.
- **Склад.** Блок «Поповнити склад» враховує матеріали лише з `minStock > 0`. Узгодити, чи нульовий мінімум означає «не відстежувати»; додати прогноз за рецептами після підтвердження правил списання.

## Технічні борги та регресійні перевірки

- `app/page.tsx` поєднує форму, навігацію, аналіз і календар. Виносити компоненти по одній функціональній межі без зміни фінансового контракту. Не додавати mock-транзакцій.
- `lib/local-data.ts` додає відсутні початкові продукти до існуючого сховища. Перевірити сценарій свідомого видалення seed-продукту: він може з'явитися знову після оновлення. Запропонувати версіоновану міграцію/архівування, не втрачати налаштувань власника.
- Зараз історична COGS залежить від поточних рецептів і середньої ціни матеріалів. Для точності потрібне призначення партії або snapshot собівартості на момент продажу. Дотримуватися окремості виручки, закупок, операційних витрат і COGS.
- `npm run lint` має чинний конфіг, але попереджає про невикористані змінні та залежності React hooks; правило `set-state-in-effect` вимкнено для поточного екрана через наявну гідратацію стану. При рефакторингу усунути причини й звузити виняток.
- Написати змістовні тести для збереження/читання продажу МК, повторної міграції seed, групування дат, залишку до оплати та зваженої середньої собівартості. Перед випуском пройти мобільний smoke test і збереження після refresh у local та Supabase режимах.
